# Reviewed quantity recovery R1

23 October 2026. PT-05 adds the internal quantity-recovery workflow for an accepted inbox file. It reviews one closing at a time; lifecycle and administrative restoration remain PT-06, native picker/review/application screens remain PT-07. [Transfer plan](ONLINE_PENDING_TRANSFER_PLAN_R1.md).

Preparation requires an already active account at the same canonical origin and account UUID as the packet. A fresh identity read and current outlet membership precede target/status reads. A file cannot choose an endpoint or authenticate. Labels are descriptive, never grants. The target's closing UUID, outlet, exact business date and menu IDs must match current server data. Preparation does not pull into the live cache or insert a draft.

Original operation status is queried in strict batches of at most 100 IDs. The client checks exact response fields, scope, count, order, IDs and actual Boolean types. Original IDs remain provenance; they are never copied into the runnable queue. Recorded prefixes are skipped, while a dependent unhandled tail retains the latest desired quantity. An impossible handled-after-unhandled order is rejected. Current-generation normal operations use new IDs after deliberate review.

The review exposes file base/revision/desired value, current server name/value/revision, file header generation, distinct original operation generations and current generation/revision/state. A generation change can be rebased only through a fresh explicit review of current data; it does not replay an old generation. All-recorded references are labelled `ALREADY_RECORDED`, including on a now-locked closing. References previously handled on this installation are labelled `ALREADY_RECOVERED_LOCALLY`; this is not a server receipt or a claim that synchronization succeeded. Proposed changes alone require a writable DRAFT and no local quantity/lifecycle/conflict work or conflicting cached UUID for the date.

Application consumes a private frozen review ticket, pins the original local session and excludes this repository's sync engine. Fresh authorization, target data, original status and local provenance must still match the review. Stale/cancelled/duplicate/account-switched callbacks do not apply. No network mutation is sent. If the server changes after the final read, the existing revision/generation/permission guards handle that race when the user later synchronizes.

Room 9 adds only `online_recovery_claims`, keyed by scope and original operation ID. A transaction rechecks target/local claims, pulls the current snapshot, creates ordinary QUEUED operations against current entry revisions and inserts provenance together. A claim records fingerprint, target, original ID, new local operation ID where applicable and local time. It is not historical server authorship. A failed claim insertion rolls back cache, entries, queue and claims together. Accepted inbox files and the original installation's queue remain intact. Claims persist after synchronization removes queue rows, so another byte representation of the same original references is still recognized locally.

This is a single-process application boundary. A server status of absent is snapshot-limited and an older sender may later commit. New drafts remain protected by optimistic revisions; a local claim does not establish global exactly-once recovery across every installation. Users can inspect original desired values and use ordinary workflows for later deliberate corrections; importing does not grant automatic overwrite rights.
